пш# Проект «Касса кофейни»: командная работа в паре

Вы пара разработчиков. Задача: сделать кассу для кофейни и при этом работать так, как работают настоящие команды: общий репозиторий на GitHub, у каждого своя ветка, Pull Request с проверкой кода партнёром, конфликт при слиянии и откат, когда что-то сломали.

**Технологию выбираете сами:** tkinter, Flet, PyQt, консольное приложение или любой другой модуль Python, который вы знаете. Код за вас здесь не написан: вы сами решаете, как его реализовать. Главное, чтобы программа выполняла задания и проходила **контрольные проверки** из раздела 2.

---

## 1. Правила команды

1. Один репозиторий на пару. Оба участника имеют в нём доступ на запись.
2. `main` всегда рабочий. Ломать можно только свою ветку.
3. **Одна ветка равна одной функции. Один коммит равен одной законченной мысли.**
4. Каждый коммит должен запускаться. Не коммитьте код, который не работает.
5. Сообщение коммита короткое, по-английски, с глагола: `Add promo code field`. Не `fix`, `123`, `asdf`, `final`.
6. В чужой ветке код не пишете. Хотите что-то изменить, пишете партнёру комментарий в Pull Request.
7. Перед началом любой работы выполните `git status` и `git pull`.

## 2. Контрольные данные (одинаковые у всех)

**Меню (минимум эти 5 позиций):**

| Блюдо | Цена, BYN |
|---|---|
| Кофе | 3.50 |
| Чай | 2.50 |
| Бургер | 7.00 |
| Картошка фри | 3.00 |
| Лимонад | 2.00 |

**Контрольный заказ: 2 бургера.** Итог после каждого этапа должен совпасть с таблицей, округление до двух знаков:

| Условия | Ожидаемый итог |
|---|---|
| Без промокода, без чаевых | 14.00 |
| Промокод `TEEN10` | 12.60 |
| Чаевые 5% | 14.70 |
| Чаевые 10% | 15.40 |
| Чаевые 15% | 16.10 |
| Промокод `TEEN10` и чаевые 10% | 13.86 |

Правило подсчёта (договорённость на всю команду): скидка считается на блюда, а чаевые считаются от суммы **после** скидки. Запишите его в `README.md`.

## Этап 2. База кассы в `main`: эстафета из 4 коммитов (30–40 минут)

Здесь вы работаете **по очереди** и прямо в `main`. Пока один пишет коммит (драйвер), второй рядом подсказывает и проверяет (навигатор), но свой компьютер не трогает.

**Порядок эстафеты:** после каждого коммита автор делает `git push`, а партнёр делает `git pull` и продолжает. Если `git push` отклонён, сначала `git pull`, потом снова `git push`.

| № | Кто | Что сделать | Сообщение коммита | Как проверить |
|---|---|---|---|---|
| 1 | Б | Хранение меню (5 позиций из раздела 2) и **одна функция, которая считает итоговую сумму заказа**. Интерфейса пока нет | `Add menu and total calculation` | Вызов функции для 2 бургеров даёт 14.00, для пустого заказа 0 |
| 2 | А | Интерфейс: список блюд, кнопка «Добавить в заказ», на экране итог | `Add order window` | Выбрали блюдо, нажали кнопку, итог изменился |
| 3 | Б | Корзина: на экране видно, что добавлено в заказ. Кнопка «Очистить заказ» | `Add cart and clear button` | Добавили 2 бургера, они видны. «Очистить» всё сбрасывает, итог 0.00 |
| 4 | А | Кнопка «Оплатить». С пустым заказом показывает красное «Заказ пуст». С заказом показывает «Оплачено: …» и очищает заказ | `Validate empty order` | Оплата пустого заказа даёт сообщение, оплата 2 бургеров показывает 14.00 |

**Важно для следующих этапов:** договоритесь, что **весь расчёт итога живёт в одной функции** (из коммита 1). Обе ваши будущие ветки будут менять именно её.

После коммита 4 участник А ставит метку «рабочая база»:

```bash
git tag v1-base
git push --tags
```

Затем **оба** убедитесь, что у вас одинаковый последний коммит: `git log --oneline -1`. Хеши (буквы и цифры в начале строки) должны совпасть.

## Этап 4. Pull Request и проверка кода партнёром (20 минут)

**Pull Request (PR)** это запрос на слияние ветки с `main`. Вы просите партнёра проверить ваш код, и только после этого он попадает в `main`.

### Автор открывает PR

1. На странице репозитория на GitHub нажмите **Compare & pull request** (жёлтая плашка вверху) или откройте вкладку **Pull requests → New pull request**.
2. Заголовок: что делает ветка. Например: «Promo code TEEN10».
3. В описании напишите три пункта: **Что сделано / Как проверить / Результат контрольного заказа**.
4. Справа в **Reviewers** выберите партнёра.
5. Нажмите **Create pull request**.

### Ревьюер проверяет PR партнёра

1. Откройте вкладку **Files changed**: что именно изменено?
2. Скачайте ветку и запустите: `git fetch`, `git switch <ветка партнёра>`. Проверьте контрольные значения из раздела 2. Вернитесь: `git switch <своя ветка>`.
3. Ответьте на вопросы проверки:
   - Программа запускается, контрольные значения верны?
   - Сообщения коммитов понятные? Один коммит равен одной идее?
   - В ветке нет лишнего (чужие файлы, `.idea`, `__pycache__`)?
   - Код понятен? Можно оставить комментарий к строке: наведите на строку, кнопка `+`.
4. Нажмите **Review changes** и выберите **Approve** (всё хорошо) или **Request changes** (нужны правки). Напишите комментарий.

### Слияние

После **Approve** участник А нажимает **Merge pull request → Confirm merge**. Сливаем **по очереди**: сначала PR `feature/promo-code`.

Участник Б после слияния пишет в PR комментарий: проверил `main` контрольным заказом, результат такой-то.

Оба обновляют `main`:

```bash
git switch main
git pull
```

**Вторым PR (`feature/tips`) пока не сливаем.** Это этап 5.

**✋ СТОП 4.** Покажите преподавателю: PR промокода слит, в нём есть Approve от партнёра.

## Этап 5. Конфликт слияния (20 минут)

Пока ваш PR `feature/tips` ждал, `main` изменился: туда влит промокод. Обе ветки меняли функцию расчёта итога и строку `Статус` в `README.md`. GitHub покажет у PR сообщение **This branch has conflicts that must be resolved**. Это нормально, мы этого и ждали.

**Решает Участник Б, но вдвоём.** Конфликты решают вместе, партнёр помогает смотреть.

1. Принесите изменения `main` в свою ветку:

```bash
git switch feature/tips
git merge main
```

   Git остановится на сообщении `CONFLICT (content): Merge conflict in ...`.

2. `git status` покажет файлы со статусом `both modified`. Запускать программу сейчас нельзя: в файлах маркеры конфликта.

3. Откройте каждый такой файл и найдите участок:

```
<<<<<<< HEAD
... версия вашей ветки (чаевые) ...
=======
... версия из main (промокод) ...
>>>>>>> main
```

4. **Задача:** оставить **обе** возможности и удалить три служебные строки (`<<<<<<<`, `=======`, `>>>>>>>`):
   - в функции расчёта итога должны работать и промокод, и чаевые (по правилу из раздела 2: скидка на блюда, чаевые от суммы после скидки);
   - в `README.md` строка `Статус` должна быть одна: **`Статус: промокоды и чаевые готовы`**;
   - сохраните все файлы.

5. **Проверка:** запустите программу, прогоните все 6 строк контрольной таблицы из раздела 2. Итог `TEEN10` вместе с чаевыми 10% должен быть **13.86**.

6. Завершите слияние и отправьте:

```bash
git add <все файлы, где был конфликт>
git commit -m "Merge main into feature/tips"
git push
```

7. Если запутались: `git merge --abort` отменяет слияние, и можно начать с шага 1.

8. Ваш PR на GitHub теперь без конфликтов. Участник А проверяет (Approve) и нажимает Merge. Участник Б комментирует результат контрольного заказа.

9. Оба: `git switch main`, `git pull`.

**✋ СТОП 5.** Покажите преподавателю: `git log --oneline --graph --all`. Должны быть видны два слияния и ваш коммит `Merge main into feature/tips`.

## Этап 7. Откат: возвращаем рабочую кассу (15 минут)

**Выполняет Участник Б** (автор сломавшей ветки). Участник А смотрит и проверяет результат.

1. Найдите коммит слияния сломавшей ветки:

```bash
git switch main
git pull
git log --oneline --graph
```

   Нужна строка вида `Merge pull request #N from .../experiment/crazy-prices` (слияние, у которого линия графа ветвится). Запишите её хеш (первые 7 символов).

2. Отмените слияние:

```bash
git revert -m 1 <хеш слияния>
git push
```

   Откроется редактор с сообщением коммита: сохраните и закройте его без изменений.

3. Что произошло:
   - git создал **новый** коммит `Revert "Merge pull request ..."`, который отменяет изменения сломавшей ветки. История не стёрта: сломанные коммиты остаются, но касса снова работает;
   - `-m 1` означает: «основной линией считай первого родителя слияния, то есть `main`». Слияние имеет двух родителей, и без этого git не поймёт, к какому возвращаться.

4. Участник А: `git pull`, запустите кассу и проверьте **все 6 строк** контрольной таблицы. Чек тоже должен продолжать работать.

### Задания на откат к версии

Выполните и **запишите ответы в `README.md`** (в раздел «Что мы узнали»):

| № | Задание | Подсказка |
|---|---|---|
| 1 | Посмотрите самую первую рабочую версию кассы и запустите её. Чем она отличается от текущей? | `git switch --detach v1-base`, запуск, потом `git switch main` |

### Для сильных пар (необязательно)

На временной ветке (**не на `main`!**) попробуйте жёсткий откат:

```bash
git switch -c test-reset
git commit --allow-empty -m "Temporary commit"
git reset --hard HEAD~1
```

   Коммит исчез из ветки. Верните его:

```bash
git reflog
git reset --hard HEAD@{1}
```

   Затем удалите временную ветку: `git switch main`, `git branch -D test-reset`. Объясните партнёру, **почему `reset --hard` нельзя делать в общей ветке** и чем он отличается от `revert`.

## Если что-то пошло не так

| Что случилось | Что делать |
|---|---|
| `git push` отклонён (`rejected`, `non-fast-forward`) | Партнёр отправил свои коммиты раньше. Сделайте `git pull`, проверьте, что всё работает, потом `git push` |
| `git push` пишет `Permission denied` или `403` | Вы не приняли приглашение или не вошли в свой аккаунт. Проверьте письмо с приглашением |
| Вы не помните, в какой вы ветке | `git branch`: звёздочка у текущей |
| Вы сделали коммит не в ту ветку (и ещё не отправили) | Позовите преподавателя или создайте новую ветку из текущего состояния: `git switch -c <правильная-ветка>`, затем вернитесь в неверную и верните её на место: `git switch <неверная>`, `git reset --hard origin/<неверная>` |
| Запутались в конфликте | `git merge --abort` и начните заново |
| Сломали ветку | Не страшно, это только ваша ветка. `main` не пострадал. Посмотрите `git log`, откатите коммит (`git revert <хеш>`) или позовите преподавателя |
| `git status` показывает лишние файлы (`.idea`, `__pycache__`, `receipt.txt`) | Добавьте их в `.gitignore` |
| Не получается запустить программу после `git pull` | Возможно, у партнёра используется модуль, которого нет у вас. Установите его (`pip install ...`) и попросите партнёра записать в `README.md` команду установки |
